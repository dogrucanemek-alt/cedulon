How Cedulon compares

Including the places where the other projects are ahead of us. Every cell says whether it comes from the project's own documents or from a function we found in its code, because those are two different kinds of evidence and a comparison written by a vendor is worth exactly as much as its verifiability.

Read this first. Cedulon is the smallest project on this page: 0 GitHub stars against x402's 6,606 and AP2's 3,176. Nothing here moves real money; the repository runs on mock fixtures and one read-only testnet window. If you need a payment rail, pick a rail. Cedulon is not one; it sits above x402 and AP2 as an audit layer. Keep reading only if what you need is a signed receipt per spend, a refusal when the policy engine is missing, and a reconciliation that finds the spend that left no receipt.

How to read a cell. Docs is what the project's documentation says. Code names the function we found producing that behaviour at the pinned commit, or says not found when we did not find one in the files we read. Not found is not proof of absence. Nothing was executed; this is a static reading of open code and public documents. Cedulon's own row is held to the same notation.

Where they are ahead of us

Five things, stated before the parts that favour us.

  • They move value; we do not. x402, AgentKit and AP2 settle payments, on chain or through mandates. Cedulon moves nothing and never will; it is an audit layer above the rail. If you need the payment itself, they are the product and we are not.
  • Adoption. 0 stars against 6,606, 3,176 and 1,801. No external production deployment we know of. Everything on this site is our own run or a reproducible test.
  • Human approval. AP2 specifies a human-present flow and Vaara ships request_approval(). Cedulon's policy answers allow or deny and has no hold state; if you need a person in the loop, that layer has to sit above Cedulon.
  • Scope. Vaara governs tool calls beyond payment. Stripe's toolkit spans a whole payments API with OAuth and restricted keys. Cedulon does one thing: gate a spend, sign the receipt, reconcile the extract.
  • Receipt formats with ecosystems. x402's JWS / EIP-712 receipts and AP2's JWT receipts live inside protocols other people implement. Cedulon's COSE_Sign1 receipt is specified in an individual Internet-Draft that no working group has adopted.

Where we are different

Different, not better. Each of these is a design choice with a cost attached.

  • Refusal is the default when the engine is gone. failClosedEvaluate() refuses for a missing engine and for a throwing one. We did not find the same guarantee stated for the others; AgentKit's empty-allowlist refusal and Vaara's scorer-exception path are the closest code we found.
  • The second ledger. We compare the rail's own extract against the receipt chain and report settlement-without-receipt. A receipt chain alone reports only what it knows about itself. We did not find a rail-extract reconciliation in any project above; a chain transaction id and internal gap detection are not the same claim.
  • A verifier document instead of a promise. docs/RUN_AS_VERIFIER.md reruns the whole suite on a clean machine without trusting us. Vaara's offline trail verify is the nearest thing on this page.
  • Stated plainly. A Cedulon receipt proves a decision was recorded and not altered afterwards. It does not prove the money moved, and a rail may succeed even if Cedulon is skipped (THREAT_MODEL.md). That gap is exactly why the reconciliation exists.

Not in the table, and why

  • Skyfire. Its features page returned HTTP 404 to us on 12 September 2026. We do not score what we could not read.
  • Payman. The policy documentation returned HTTP 526 and the dashboard guide 404 on 12 September 2026. The rule quoted elsewhere as "no policy, no access" could not be re-read, so it is not in the table.
  • Nekuda. The current product is a WebMCP kit for typed website tools; we did not find a payment audit engine to score.
  • Visa Intelligent Commerce. Detailed documentation is behind restricted access; the public page describes agent tokens and their lifecycle, not enough to fill the columns.
  • Mastercard Agent Pay. The public page describes credentials and pre-authorisation and returned HTTP 403 to our fetch; the developer toolkit on GitHub explores APIs and is not the execution engine.
