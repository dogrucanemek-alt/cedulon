7	          Cedulon: An Audit Layer for Agent-to-Agent Commerce
8	                         draft-dogru-cedulon-03

10	Abstract

12	   This document defines the Cedulon Protocol, an audit layer for agent-
13	   to-agent commerce.  Payment rails such as HTTP 402 flows (x402) and
14	   mandate protocols (AP2) already move value.  They do not, by
15	   themselves, produce a fail-closed policy check and a signed spend
16	   receipt that a verifier can reconcile against a rail extract.
17	   Cedulon specifies a Trade Manifest (signed offer before payment), a
18	   Policy Decision Point with default deny, a Spend Receipt (COSE/CWT
19	   claim set after a gated payment), epoch checkpoints, and rail-extract
20	   reconciliation.  The reconciliation shows that no settlement on the
21	   extract lacks a receipt and no settled receipt is absent from the
22	   extract.  That result is unconditional only when the verifier pins
23	   the rail key out of band and states the period under audit; otherwise
24	   the document requires it to be reported as conditional.  Checkpoints
25	   carry the suppression guarantee, so this revision profiles the
26	   checkpoint as a Signed Statement, gives the verification algorithm a
27	   step that consumes the transparency receipts returned for
28	   checkpoints, names what a witness holding a checkpoint the presented
29	   chain omits reports, brings equivocation within reach by comparing
30	   recorded copies against the presented chain, and states how
31	   checkpoint totals may be withheld without withholding the fact that
32	   they were.  It also defines a Dispute Evidence Bundle (evidence, not
33	   an award) and optional SCITT anchoring.  Cedulon is not a competitor
34	   to x402 or AP2; it sits above them.

132	1.  Introduction

134	   _Note to Readers:_ This document is submitted as Informational.  The
135	   author's eventual intended track, if the work is taken up, is a
136	   Standards Track profile of COSE [RFC9052] and CWT [RFC8392] for
137	   agent-spend receipts.  This -02 does not claim IETF consensus.

139	   Agents can now pay.  Open HTTP 402 protocols [X402] attach stablecoin
140	   settlement to ordinary requests.  Card networks and processors issue
141	   agent-scoped tokens.  Google's Agent Payments Protocol (AP2) [AP2]
142	   binds user intent to signed mandates.

144	   What is missing is an interoperable *audit layer*: a machine-
145	   checkable answer to "was this spend allowed by policy, against which
146	   offer, and what bytes were delivered?"  Without that layer, a prompt-
147	   injected or looping agent can drain a rail that has already accepted
148	   a valid signature.  A counterparty can ship the wrong artifact.  A
149	   transparency log, if used at all, is proprietary.

151	   Cedulon fills that gap.  It does not clear funds, hold custody, or
152	   operate a payment facilitator.  An optional escrow actor is defined
153	   only as a third-party role interface (Section 15.13).
154	   Implementations of this specification MUST NOT take custody of funds
155	   or operate escrow (MUST-T8-custody).

157	   The control is an old one.  Reconciling an internal ledger against an
158	   external statement is what double-entry bookkeeping [PACIOLI] made
159	   routine, and signing the artifacts on both sides is Grigg's triple-
160	   entry idea [GRIGG].  Neither is claimed here.  What this document
161	   contributes is an open wire profile for that control in a setting
162	   where the parties are software: a COSE receipt shape, an extract
163	   shape, a checkpoint chain, and a verification algorithm precise
164	   enough that two implementations reach the same finding on the same
165	   evidence.  The novelty is interoperability, not the idea.

167	   Neighbor drafts are complementary, not substitutes. draft-bates-atp
168	   [BATES-ATP] covers tamper-evident causal lineage as a signed DAG.
169	   Cedulon is the completeness layer: a spend that never produced a
170	   receipt is visible when an authenticated rail extract is reconciled
171	   (MUST-T10-1).

173	2.  Terminology

175	   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
176	   "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and
177	   "OPTIONAL" in this document are to be interpreted as described in
178	   BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all
179	   capitals, as shown here.

181	   The following terms are used:

183	   Trade Manifest:  A signed statement produced *before* payment.  It
184	      binds a description of goods or service, price, currency,
185	      acceptance-criteria hash, cancel condition, expiry, and an
186	      optional AP2 mandate reference.

188	   Policy Decision Point (PDP):  The function that evaluates a
189	      structured spend request against stored policy.  The default is
190	      deny.

192	   Spend Receipt:  A signed statement produced *after* a gated payment
193	      attempt.  It binds payer, payee, amount, currency, policy hash,
194	      manifestHash or an explicit noManifest flag, rail payment
195	      reference, timestampMs, nonce, prevReceiptHash, and outcome.

197	   Receipt Issuer:  The party that signs Spend Receipts.

199	   Anchor:  An optional SCITT Transparency Service [RFC9943] that
200	      registers a signed statement and returns a COSE receipt [RFC9942].

202	   Dispute Evidence Bundle:  A package of the Trade Manifest, the Spend
203	      Receipt, and a delivery hash.  It is evidence for a later human or
204	      legal process.  It is not an arbitral award and not an escrow
205	      release.

207	   Decision Token:  A portable, single-use PDP allow encoded as
208	      COSE_Sign1.  The claim set binds requestHash, policyHash,
209	      expiryMs, nonce, and singleUseId.  See Section 7.

211	   Rail Extract:  An authenticated list of settlement records for one
212	      account, one rail, and one time window.  See Section 8.

214	3.  Architecture

216	   Cedulon has three control-plane objects and one optional log:

218	     Principal --policy--> PDP --allow/deny--> x402/AP2 rail
219	                                 |
220	                                 v
221	                         Receipt Issuer --> Spend Receipt
222	                                 |
223	                                 v
224	                         Anchor / SCITT (optional)

226	   The payer agent never talks to the rail except through an adapter
227	   that calls the PDP first (MUST-T5-1).

229	3.1.  Policy Decision Point

231	   The PDP evaluates structured fields only (MUST-T1-1): amount,
232	   currency, payee, tool identifier, nonce, optional manifest hash, and
233	   evaluation time.  It applies limit, velocity, and scope checks (MUST-
234	   T2-1, MUST-T2-2).  If the PDP is unreachable, uninitialized, or
235	   throws, the result is deny (MUST-T2-3).  Denied attempts do not
236	   increment success counters (MUST-T2-4).

238	   An allow produces a Decision Token whose requestHash covers six
239	   fields: amount, currency, payee, tool, nonce, and manifestHash (MUST-
240	   T3-4, MUST-T6-1).  The token is a COSE_Sign1 object (MUST-T6-4), is
241	   single-use (MUST-T6-2), and MAY be carried to the adapter that
242	   performs settlement.

244	3.2.  Receipt Issuer

246	   After the adapter attempts settlement (success or a recorded deny
247	   that still needs an audit trail for an allowed-then-aborted path),
248	   the Receipt Issuer signs a Spend Receipt over a canonical encoding
249	   (MUST-T4-1).  Verifiers reject bad signatures and byte mismatch
250	   (MUST-T4-2).

252	3.3.  Anchor / SCITT

254	   Parties MAY register the signed receipt (or a privacy-preserving hash
255	   encoding) as a SCITT Signed Statement [RFC9943] and attach the COSE
256	   receipt (MAY-T4-6).  This document does not operate a Transparency
257	   Service.

259	4.  Trade Manifest

261	   A Trade Manifest is the commerce analogue of a promise: it is issued
262	   *before* value moves.  It is conceptually symmetric to a later Spend
263	   Receipt (promise then proof), and it MAY carry an AP2 mandate hash so
264	   that user intent and the Cedulon offer stay linked (SHOULD-T8-5).

266	   A Trade Manifest MUST bind all of the following (MUST-T8-1):

268	   *  goods or service description

270	   *  price (integer minor units, encoded as a decimal string matching
271	      0|[1-9][0-9]*)

273	   *  currency (ISO 4217 alphabetic or a documented token identifier)

275	   *  acceptance-criteria hash (SHA-256 [RFC6234] of the exact delivery
276	      bytes or of a declared schema instance)

278	   *  cancel condition (opaque string agreed by the parties)

280	   *  expiry (POSIX milliseconds, expiresAtMs)

282	   It MAY include ap2MandateHash.  The corresponding CBOR label is
283	   always present; a missing mandate is encoded as CBOR null.

285	   The manifest is COSE_Sign1 [RFC9052] over a deterministic CBOR claim
286	   map (Section 6). manifestHash is the SHA-256 of the signed COSE bytes
287	   (MUST-T8-7).  A spend bound to a manifest MUST be denied if the
288	   requested amount or currency differs from the manifest (MUST-T8-2) or
289	   if the manifest is expired (MUST-T3-3).

291	   A spend that is not bound to a verified manifest MUST be marked
292	   noManifest on the receipt and MUST still pass limit, velocity, and
293	   scope checks (MUST-T1-2).  An implementation MAY refuse all
294	   noManifest spend (MAY-T1-4).

296	5.  Spend Receipt

298	   The Spend Receipt claim set is carried in COSE_Sign1 [RFC9052]
299	   wrapping a CWT-compatible map [RFC8392].  New receipts MUST use the
300	   COSE profile (Section 6).

302	   Claims (MUST-T4-3, MUST-T4-4, MUST-T4-7):

312	    +-----------------+-----------------------------------------------+

316	    |                 | (lowercase hex)                               |

319	    |                 | null when noManifest is true                  |

339	   A receipt with outcome = settled MUST have a non-null x402PaymentRef
340	   (MUST-T4-7).  An aborted receipt MUST NOT be added into checkpoint
341	   totals.

343	   All twelve labels in Section 6.1 are always present.  An empty
344	   optional value is encoded as CBOR null, never by omitting the label.

346	   receiptHash is the SHA-256 of the receipt's signed COSE bytes,
347	   encoded as lowercase hex.

349	   Verifiers MUST reject a receipt if the signature fails or if the
350	   decoded claim map does not match the presented claims (MUST-T4-2).

352	5.1.  Optional payee countersignature

354	   A payee MAY attach a countersignature over the issuer's signed Spend
355	   Receipt (MAY-T8-9).  The profile uses a *detached* COSE_Sign1
356	   [RFC9052] whose payload is a CBOR map with a single private-use
357	   label:

359	      +========+=============+======================================+
360	      | Label  | Claim       | CBOR type                            |
361	      +========+=============+======================================+
362	      | -70401 | receiptCose | bstr (exact issuer COSE_Sign1 bytes) |
363	      +--------+-------------+--------------------------------------+

365	                                  Table 2

367	   The countersignature uses the header profile in Section 6 and content
368	   type application/cedulon-countersign+cbor.

370	   This is a second Sign1 object, not RFC 9052 Countersignature0
371	   (unprotected-header label 11).  Countersignature0 would write into
372	   the issuer object and change receiptHash after issue, breaking the
373	   receipt chain.  A detached Sign1 keeps the issuer bytes stable,
374	   reuses kid and content-type, and is absent by simply omitting the
375	   sibling object.

377	   Absence of a countersignature MUST NOT invalidate the issuer receipt
378	   (MAY-T8-9).  If a countersignature is present, a verifier MUST reject
379	   it when the signature fails, when kid or content type does not match
380	   the configured payee key, or when label -70401 is not the issuer COSE
381	   bytes (MUST-T8-8).  The identifier countersign-bad SHOULD be used for
382	   this condition.  A Dispute Evidence Bundle that includes a verified
383	   countersignature has stronger evidence that the payee accepted those
384	   bytes; the bundle is still not an award (MUST-T8-4).

386	6.  COSE Profile

388	   This profile uses deterministic CBOR [RFC8949] Section 4.2.1
389	   (definite lengths, shortest integer form, map keys sorted in
390	   *bytewise lexicographic* order of their encoded keys).
391	   Implementations MUST encode only the types used by Cedulon claim
392	   maps: null, bool, unsigned and negative integers, UTF-8 text, byte
393	   strings, arrays, and maps (MUST-T4-1).

495	6.2.  COSE_Sign1 headers

497	   The protected header MUST be a deterministic CBOR map containing
498	   (MUST-T4-1, MUST-T4-8):

500	   *  1 (alg) = -19 (Ed25519, [RFC9864]; the generic EdDSA value -8 from
501	      [RFC9053] is deprecated for this profile)

503	   *  3 (content type) = a tstr that distinguishes the payload:
504	      application/cedulon-receipt+cbor, application/cedulon-
505	      checkpoint+cbor, application/cedulon-manifest+cbor, application/
506	      cedulon-decision+cbor, or application/cedulon-countersign+cbor

508	   *  4 (kid) = bstr, mandatory.  The profile computes kid as the first
509	      eight bytes of SHA-256 over the issuer's SubjectPublicKeyInfo DER.
510	      A verifier MUST obtain the public key from an authenticated
511	      channel (preconfigured issuer set, directory, or transparency
512	      statement) and MUST reject a message whose kid does not match that
513	      key.

515	   The unprotected header MUST be empty.  The payload MUST be the CBOR
516	   encoding of the claim map.  The signature is Ed25519 [RFC8032] over
517	   the COSE Sig_structure ["Signature1", protected, h'', payload].

519	7.  Decision Token

521	   A Decision Token is the portable encoding of a PDP allow.  It is
522	   COSE_Sign1 with the header profile in Section 6 and the labels in
523	   Section 6.1.  All five labels are always present (MUST-T6-4).

525	   requestHash MUST be the six-field hash defined for the PDP (MUST-
526	   T6-1). policyHash MUST be the SHA-256 of the canonical policy
527	   document the PDP evaluated. expiryMs is a Unix time in milliseconds
528	   after which the token MUST be treated as expired (SHOULD-T6-3). nonce
529	   is the request nonce. singleUseId is the identifier consumed on the
530	   first settlement attempt (MUST-T6-2).

532	   A party that accepts a Decision Token MUST reject it if the signature
533	   fails, if kid does not match a configured PDP key, if the content
534	   type is not application/cedulon-decision+cbor, if the decoded claim
535	   map does not match the presented claims, or if expiryMs is in the
536	   past (MUST-T6-5).

538	8.  Rail Extract Profile

540	   A verifier checks completeness against a *rail extract*, not against
541	   the issuer's own receipts alone (MUST-T10-7).

543	8.1.  Record schema

545	   Each settlement record MUST contain:

547	              +=============+===============================+
548	              | Field       | Type                          |
549	              +=============+===============================+
550	              | ref         | tstr (rail payment reference) |
551	              +-------------+-------------------------------+
552	              | amount      | tstr matching 0|[1-9][0-9]*   |
553	              +-------------+-------------------------------+
554	              | currency    | tstr                          |
555	              +-------------+-------------------------------+
556	              | timestampMs | uint                          |
557	              +-------------+-------------------------------+

559	                                  Table 7

561	8.2.  Scope

563	   An extract is scoped to one account identifier, one rail identifier,
564	   and one half-open time window [windowStartMs, windowEndMs).

566	8.3.  Authentication

568	   The mock rail in the companion implementation signs the extract with
569	   Ed25519 over a canonical encoding of the scoped body.  A verifier
570	   MUST obtain the extract from the rail or from a signature the rail
571	   published (MUST-T10-7).  A deployment that cannot do so is running
572	   the reconciliation against evidence it did not obtain independently,
573	   and MUST report the guarantee as conditional.

575	   A signature on an extract proves internal consistency, not origin: a
576	   key generated by whoever produced the object verifies against itself.
577	   The verifier therefore MUST obtain the rail's public key out of band
578	   and MUST verify the extract signature against that key rather than
579	   against any key the extract carries (MUST-T10-8).  A verifier that
580	   holds no such key MUST treat the guarantee as conditional.

582	   Keys are compared as bytes.  A verifier MUST compare the pinned key
583	   and the key that signed the extract by their SubjectPublicKeyInfo DER
584	   encoding, not by any text encoding of it, so that the same key
585	   presented in a different envelope still compares equal (MUST-T10-9).
586	   A pinned key the verifier cannot decode is a fault in the verifier's
587	   own configuration, not evidence about the extract, and MUST be
588	   reported as trust-key-unreadable rather than as a key mismatch.

590	   What a verifier emits for an extract it cannot authenticate depends
591	   on whether it stated an expectation.  With no pinned key the verifier
592	   has asserted nothing, so an extract that does not carry a verifiable
593	   signature is unauthenticated-extract, a warning: completeness
594	   findings may still be computed, but the guarantee is *conditional* on
595	   the extract being authentic.  With a pinned key the verifier has
596	   asserted what it requires, and an extract that fails to meet it is a
597	   failure rather than a caveat; see the verification algorithm for
598	   which finding applies. -00 defined only the first case, and readers
599	   of -00 should note that this revision makes the pinned case fail
600	   closed.  See Section 15.

602	8.4.  Scope agreement

604	   An extract declares a window and carries settlement records.  The two
605	   MUST agree: a verifier MUST report every settlement record whose
606	   timestampMs falls outside [windowStartMs, windowEndMs) as extract-
607	   scope-mismatch, identified by that record's ref (MUST-T10-10).  This
608	   check is about the extract's internal consistency and MUST be
609	   performed whether or not a rail key is pinned.

611	   A verifier that knows which account, rail, and window it is auditing
612	   MUST also check the extract against that expectation and MUST fail
613	   closed when the extract does not cover it (MUST-T10-11).  An extract
614	   for another account or rail, or one whose window does not span the
615	   period under audit, cannot support a completeness claim about that
616	   period.

618	   A verifier that states no period leaves the extract free to define
619	   one, and an extract that reports on a millisecond balances as easily
620	   as one that reports on a month.  Pinning a key establishes who
621	   signed; only a stated period establishes what the signature had to
622	   cover.  A verifier that has not stated the period under audit
623	   therefore MUST emit unstated-audit-window and MUST treat the
624	   guarantee as conditional (MUST-T10-15), whatever else verifies.

626	9.  Trust roots

628	   Section 8 states the rule for one object: a signature proves internal
629	   consistency, not origin, so the verifier obtains the rail key out of
630	   band and checks the extract against that key rather than against any
631	   key the extract carries (MUST-T10-8). -02 already required a verifier
632	   to obtain the public key from an authenticated channel and to reject
633	   a kid that does not match that key (MUST-T4-8).  What -02 did not
634	   carry was the verification algorithm, the separate root inputs, and
635	   the error semantics that name a missing or mismatched pin.  This
636	   section states those for every signed object in the profile.

638	   The gap is not theoretical.  A verifier that checks a Spend Receipt
639	   against the key the receipt carries accepts a receipt signed by any
640	   key at all, including one an attacker minted for the occasion.  Such
641	   a receipt matches a settlement the attacker was never authorised to
642	   make, the settlement stops looking uncovered, and the audit reports
643	   nothing.  The completeness property in Section 10 is then computed
644	   over evidence that answers to nobody.

646	9.1.  The issuer root

648	   A verifier MUST obtain the issuer's public key out of band and MUST
649	   verify Spend Receipt and epoch checkpoint signatures against that key
650	   rather than against a key the object carries (MUST-T4-9).  A verifier
651	   that holds no such key and is presented with any Spend Receipt or
652	   epoch checkpoint MUST treat the completeness guarantee as conditional
653	   and SHOULD report the condition; the identifier unauthenticated-
654	   issuer is used for it in this implementation.

656	   The condition names those two objects because an audit given no
657	   receipts and no checkpoints rests on the extract alone.  There the
658	   absent issuer root withholds nothing, and warning about a root the
659	   audit never consulted would spend the warning where it carries no
660	   information.

662	   Reporting a mismatch is not sufficient on its own.  A receipt that
663	   does not answer to the pinned issuer key MUST NOT count as coverage
664	   for the settlement it names, and the settlement MUST still be
665	   reported as uncovered (MUST-T4-10).  A verifier that reports the
666	   mismatch and then lets the receipt match the settlement anyway has
667	   described the attack in its output while still concluding that the
668	   books balance.

670	   Keys are compared as bytes, by their SubjectPublicKeyInfo DER
671	   encoding, on the same terms as MUST-T10-9.  A pinned issuer key the
672	   verifier cannot decode is a fault in its own configuration and MUST
673	   be reported as trust-key-unreadable rather than as a mismatch against
674	   the objects; where no pinned key can be decoded at all, nothing is
675	   attested and the verifier MUST NOT fall back to accepting the keys
676	   the objects carry (MUST-T4-11).  Falling back is how a mistyped
677	   configuration becomes a bypass.

679	   A verifier MUST accept an issuer root that is a set of keys rather
680	   than a single key (MUST-T4-12).  An issuer that rotates its key mid-
681	   window otherwise produces a finding against every honest receipt
682	   signed by the retired key, and the reachable way out of that is to
683	   stop pinning, which is the opposite of what the pin is for.

685	9.2.  The payee root

687	   The optional countersignature in Section 5.1 travels beside the
688	   issuer signature without being covered by it.  Anyone holding an
689	   honest receipt can append a countersignature of their own, so a
690	   verifier that checks it against the key carried next to it learns
691	   only that some key signed something.

693	   A countersignature MUST NOT be treated as evidence that the payee
694	   approved the payment unless it verifies against a payee key the
695	   verifier obtained out of band (MUST-T4-13).  Without such a key the
696	   verifier SHOULD report the condition and MUST treat the guarantee as
697	   conditional.

699	   Naming a payee key states an expectation, and an expectation that
700	   only fires when the evidence is present can be cancelled by deleting
701	   the evidence.  Where a verifier has pinned a key for a payee, a
702	   settled receipt naming that payee and carrying no countersignature
703	   MUST be reported (MUST-T4-14).  Otherwise an attacker removes their
704	   own failed forgery and the report returns to unconditional.

706	9.3.  The witness root

708	   Section 10.3 describes what a transparency witness adds.  An
709	   inclusion receipt checked against the key it carries says that some
710	   log is internally consistent, and a log is cheap to invent.

712	   A verifier MUST obtain the transparency service's public key out of
713	   band and MUST verify inclusion receipts against it (MUST-T11-15).
714	   Inclusion receipts that cannot be checked that way MUST NOT be used
715	   as evidence, in either direction: they cannot establish that a
716	   checkpoint was anchored, and they cannot establish that one was
717	   withheld.  A verifier SHOULD report that it left them out.

719	   A log holds statements from everyone who uses it.  A statement held
720	   by a pinned log MUST additionally answer to the issuer root before it
721	   counts as something that issuer published (MUST-T11-16); otherwise
722	   another user's epoch, sitting in a shared log, reads as this issuer
723	   publishing two checkpoints for one epoch.

725	   Anchoring and withholding are different claims and need different
726	   evidence.  Establishing that a checkpoint was logged needs only the
727	   statement hash.  Establishing that an issuer withheld one needs to
728	   know whose statement it is, which an inclusion receipt carrying no
729	   statement body cannot say.  Such a receipt MUST NOT be used to report
730	   a withheld checkpoint, and MUST NOT be silently discarded either: a
731	   real withholding must not be buried by removing the body (MUST-
732	   T11-17).

734	9.4.  The decision root

736	   A Decision Token is issued by the policy decision point and consumed
737	   by the same deployment.  The consumer therefore holds the key it
738	   signs with and has no reason to ask the token which key to check it
739	   against.  A consumer MUST verify a Decision Token against its own
740	   issuing key and MUST NOT accept one it cannot check that way (MUST-
741	   T6-6).

743	9.5.  The manifest root

745	   A Trade Manifest is optional.  A deployment that presents none is not
746	   missing a root, and this requirement does not make such an audit
747	   conditional.  The forbidden case is the other one: a manifest is
748	   presented, and the verifier accepts it because the key travelling
749	   inside it verifies against itself.

751	   A verifier that is presented with a Trade Manifest MUST obtain the
752	   publisher's public key out of band and MUST verify the manifest
753	   signature against that key, not against a key the manifest carries
754	   (MUST-T4-15).  A verifier without such a key that is presented with a
755	   Trade Manifest MUST report the completeness guarantee as conditional
756	   and SHOULD report the condition; the identifier unauthenticated-
757	   manifest is used for it in this implementation.  An audit presented
758	   with no Trade Manifest is not made conditional by this requirement.

760	   A pinned manifest key the verifier cannot decode is a fault in its
761	   own configuration and MUST be reported as trust-key-unreadable rather
762	   than as a mismatch, on the same terms as MUST-T4-11.  A manifest that
763	   does not verify against a readable pin MUST be reported as manifest-
764	   key-mismatch and MUST fail the audit.  Falling back to the key the
765	   manifest carries is how a presented document becomes a bypass.

767	9.6.  What the roots do not cover

769	   A verifier that supplies none of these roots is not making an error,
770	   and this document does not require it to.  It is making a weaker
771	   statement, and the guarantee it reports must say so.  With no issuer
772	   key nothing distinguishes one submitted receipt from another, so
773	   conditions computed across the submitted set - two receipts claiming
774	   one settlement reference, for instance - cannot be attributed to
775	   anyone and are reported as conditions of the submission rather than
776	   as failures of a party.

778	10.  Reconciliation and Epoch Checkpoints

780	   Completeness is the property that, given an authenticated rail
781	   extract, every settlement in the extract has a matching settled Spend
782	   Receipt, every settled receipt has a matching settlement, receipt and
783	   checkpoint hash chains verify, and checkpoint totals equal the sum of
784	   *settled* receipts in the checkpoint window.  If a spend occurred
785	   without a receipt, the missing receipt is itself the evidence (MUST-
786	   T10-2).

788	   A checkpoint published with its totals withheld (Section 10.1) cannot
789	   contribute the last of those to the property.  It is not a violation
790	   of completeness and it is not a demonstration of it either: the
791	   comparison was not made, and a result that rests on a comparison
792	   nobody made is conditional (MUST-T11-12).

794	10.1.  Checkpoint claims

796	   An epoch checkpoint MUST be COSE_Sign1-signed with the header profile
797	   in Section 6 and MUST bind all of the following (MUST-T11-1):

799	   epoch, startMs, endMs, receiptCount, chainHeadHash, totals, and
800	   prevCheckpointHash.

802	   The checkpoint window is half-open [startMs, endMs) (MUST-T11-7).
803	   receiptCount MUST equal the number of receipts (settled and aborted)
804	   whose timestampMs falls in that window. chainHeadHash MUST equal
805	   receiptHash of the last receipt in that window, or null if the window
806	   is empty (MUST-T11-2).  Where totals is present it MUST sum only
807	   receipts with outcome = settled; the one permitted absence is the
808	   signed redaction below.

810	   An issuer that publishes a checkpoint without its totals MUST encode
811	   totals as null in the signed payload (MUST-T11-12).  An empty map is
812	   an honest zero for an empty window and is not a redaction.  Because
813	   the redaction is inside the signature, it cannot be added to, or
814	   removed from, a checkpoint after signing.

816	   A verifier MUST NOT accept a redaction asserted anywhere but the
817	   signed payload (MUST-T11-13).  A presentation-layer flag alongside a
818	   checkpoint is chosen by whoever presents it, which is the party under
819	   audit; honouring such a flag would let that party switch off the
820	   totals comparison for a checkpoint whose signed totals are wrong.
821	   The structural claims (epoch, startMs, endMs, receiptCount,
822	   chainHeadHash, prevCheckpointHash) MUST NOT be redacted: a checkpoint
823	   missing any of them does not decode, and a verifier MUST treat it as
824	   a failed checkpoint rather than as a redacted one.

826	10.2.  Genesis and continuity

828	   The first checkpoint in a presented chain is the genesis checkpoint
829	   of that chain.  Its prevCheckpointHash MUST be null.  Epoch numbers
830	   MUST be consecutive integers.  Adjacent windows MUST satisfy
831	   next.startMs = prev.endMs (MUST-T11-8).

833	   A later checkpoint that omits a prefix of earlier epochs (prefix
834	   deletion) is detectable only if an external witness (transparency
835	   log) has recorded the missing prefix (MUST-T11-9).  Without that
836	   witness, T11 guarantees about suppression are *conditional*.

838	   -01 stated that dependency and stopped there: nothing in its
839	   verification algorithm read a transparency receipt, so the witness
840	   had no way to speak.  This revision gives it one.  A verifier that
841	   holds transparency receipts for the period under audit compares what
842	   the witness recorded against what the chain presented, and reports
843	   the difference under its own name (Section 10.3).  A witness that
844	   holds a checkpoint the presented chain omits is not the same
845	   condition as a chain that leaves a gap in its own coverage, and the
846	   two MUST NOT be reported under one identifier (MUST-T11-11).  The
847	   first says evidence is being withheld; the second says the evidence
848	   shown is incomplete.  An operator who cannot tell them apart cannot
849	   tell an incomplete record from a concealed one.

851	10.3.  The transparency witness

853	   A checkpoint registered with a Transparency Service [RFC9943] is a
854	   Signed Statement whose payload is the checkpoint COSE object and
855	   whose content type is application/cedulon-checkpoint+cbor
856	   (Section 13).  The service returns a receipt [RFC9942] that binds the
857	   statement it recorded.

859	   A verifier MAY be given such receipts for the period under audit.  It
860	   is a distinct input from the presented checkpoint chain, and
861	   supplying it is optional: a verifier given none performs the same
862	   steps, and reports the same findings, that it would if this input did
863	   not exist (MUST-T11-10).  Supplying an empty set is not the same as
864	   supplying none.  An empty set says a witness is configured and
865	   recorded nothing, which is itself reportable; absence says no witness
866	   was consulted.

868	   A receipt binds a statement hash, not a statement.  The body is not
869	   carried by the receipt and a verifier will often not hold it.  Two
870	   levels of checking follow from that, and they are not the same (MUST-
871	   T11-10).

873	   Every receipt MUST have its signature verified before it counts for
874	   anything.  That is what establishes the hash as one the service
875	   signed for, and it is all that comparing recorded hashes against
876	   presented ones requires: the verifier computes the statement hash of
877	   each presented checkpoint itself.

879	   A receipt accompanied by the statement body carries more, and MUST be
880	   checked further before that body is relied on.  The body's statement
881	   hash MUST equal the hash the receipt binds, and the body MUST itself
882	   verify as a checkpoint.  A body that fails either check proves
883	   nothing and MUST be ignored rather than counted, while the receipt it
884	   came with remains usable for the hash comparison.  Equivocation is
885	   the case that needs a body, because it compares claims rather than
886	   hashes.

888	   What such a receipt establishes, and what it does not, is worth
889	   stating plainly.  It establishes that the service signed for that
890	   statement.  Whether the statement is a member of an append-only log,
891	   and whether that log has ever equivocated, are properties of the
892	   service and its own proofs, not of Cedulon.  A verifier that treats a
893	   signed receipt as proof of log membership is claiming more than the
894	   receipt carries.

896	10.4.  Verification algorithm

898	   A verifier MUST perform all of these steps and MUST report every
899	   finding they produce (MUST-T10-1, MUST-T11-2).  They are numbered for
900	   reference, not to require an evaluation order: no step short-circuits
901	   another, and an implementation may evaluate them in any order that
902	   produces the same set of findings.

904	   One data dependency is worth naming, because "any order" read naively
905	   would break it.  Step 15 decides which transparency receipts, and
906	   which statement bodies, survive checking.  Steps 14 and 16 consume
907	   what survives.  An implementation that ran step 14 against unchecked
908	   bodies, or step 16 against unchecked receipts, would not produce the
909	   same set of findings, so that order is not among the permitted ones.
910	   Nothing else in this list feeds another step.

912	   When a step names an identifier in backticks, that identifier SHOULD
913	   be used for the condition in diagnostic output.  The normative
914	   requirement is the behaviour: report the condition, identified by the
915	   ref or other handle given in the step.  The identifiers are not an
916	   interoperability surface.

918	   1.   Establish the subject of the audit.  When an extract is
919	        supplied, the settlement records it carries are the ones
920	        reconciled; a settlement list from any other source MUST NOT be
921	        substituted for them (MUST-T10-12).  If the caller supplies both
922	        and they differ, the verifier MUST report that the caller-
923	        supplied list disagrees with the extract, and MUST still
924	        reconcile the extract.  The identifier extract-settlement-
925	        mismatch SHOULD be used for this condition in diagnostic output.

927	   2.   Verify the extract signature against the out-of-band rail key
928	        (MUST-T10-8, MUST-T10-9).  If no key is pinned, the verifier
929	        MUST treat the completeness guarantee as conditional (MUST-
930	        T10-7).  The identifier unauthenticated-extract SHOULD be used
931	        for this condition in diagnostic output.  If a key is pinned and
932	        cannot be decoded, the verifier MUST report that the pinned key
933	        is unreadable.  The identifier trust-key-unreadable SHOULD be
934	        used for this condition.  If a key is pinned and the signature
935	        does not verify against it, or verifies against a different key,
936	        the verifier MUST report that the extract is not signed by the
937	        pinned key.  The identifier extract-key-mismatch SHOULD be used
938	        for this condition.  A finding that puts the extract itself in
939	        doubt MUST prevent an unconditional guarantee.

941	   3.   Check scope.  The verifier MUST report each settlement record
942	        whose timestampMs falls outside the declared window, identified
943	        by that record's ref (MUST-T10-10).  When the verifier states an
944	        expected account, rail, or window, it MUST report an extract
945	        that does not cover it (MUST-T10-11).  The identifier extract-
946	        scope-mismatch SHOULD be used for both conditions.  If the
947	        verifier stated no period, it MUST treat the guarantee as
948	        conditional (MUST-T10-15).  The identifier unstated-audit-window
949	        SHOULD be used for this condition.

951	   4.   Decode each Spend Receipt COSE_Sign1.  Reject if Ed25519 verify
952	        fails, if kid does not match the configured issuer key, if the
953	        content type is not the receipt type, or if the decoded claim
954	        map does not match the presented claims (MUST-T4-2, MUST-T4-8).
955	        Then apply the issuer root (Section 9.1): verify the signature
956	        against the out-of-band issuer key rather than the key the
957	        receipt carries.  A receipt that does not verify against it is
958	        reported and is excluded from the reconciliation that follows,
959	        so the settlement it names is still reported as uncovered in
960	        step 8 (MUST-T4-9, MUST-T4-10).  With no issuer key pinned the
961	        verifier makes no such distinction and reports that it did not;
962	        where any receipt or checkpoint was presented, the guarantee is
963	        conditional on the terms in Section 9.1.  Where a
964	        countersignature is present, Section 9.2 governs what it
965	        establishes (MUST-T4-13, MUST-T4-14).  Where a Trade Manifest is
966	        presented, Section 9.5 governs it (MUST-T4-15): with no
967	        publisher key pinned the verifier reports unauthenticated-
968	        manifest and the guarantee is conditional; with a pin that
969	        cannot be read, trust-key-unreadable; with a pin the manifest
970	        does not answer to, manifest-key-mismatch.  An audit presented
971	        with no Trade Manifest is not made conditional by this step.

973	   5.   Scope the receipts.  When an extract is supplied, only receipts
974	        whose timestampMs falls in the extract's declared window are
975	        reconciled against it (MUST-T10-16).  A receipt outside that
976	        window is not a completeness failure against this extract;
977	        auditing a longer period requires extracts that cover it.
978	        Receipts remain subject to every other check regardless of
979	        window.

981	   6.   Walk receipts in issuer order.  The first prevReceiptHash MUST
982	        be null.  Each later prevReceiptHash MUST equal receiptHash of
983	        the previous receipt.  A miss MUST be reported as a break in the
984	        receipt chain.  The identifier receipt-chain-break SHOULD be
985	        used for this condition.

987	   7.   Index settled receipts and extract records by ref.  A ref that
988	        appears more than once on either side MUST be reported as a
989	        repeated reference (MUST-T10-6).  The identifier duplicate-ref
990	        SHOULD be used for this condition.

992	   8.   For each ref that appears exactly once on each side, require a
993	        one-to-one match on ref AND amount AND currency (MUST-T10-1).
994	        Amount or currency mismatch MUST be reported as a settlement
995	        that does not match its receipt, identified by that ref.  The
996	        identifier settlement-mismatch SHOULD be used for this
997	        condition.  A settlement with no receipt MUST be reported as
998	        lacking a receipt, identified by its ref (MUST-T10-2).  The
999	        identifier settlement-without-receipt SHOULD be used for this
1000	        condition.  A settled receipt with no extract row MUST be
1001	        reported as a completeness failure (MUST-T10-3).  The identifier
1002	        receipt-without-settlement SHOULD be used for this condition.  A
1003	        settled receipt with a null rail ref MUST be reported as settled
1004	        without a rail reference.  The identifier settled-without-ref
1005	        SHOULD be used for this condition.

1007	   9.   A ref already reported as repeating MUST still be reconciled by
1008	        amount rather than dropped from the comparison (MUST-T10-13).
1009	        For each currency under that ref, compare the total settled
1010	        against the total receipted.  A settled total that exceeds the
1011	        receipted total MUST be reported as a settlement lacking a
1012	        receipt, and the finding MUST state the unaccounted amount.  The
1013	        identifier settlement-without-receipt SHOULD be used for this
1014	        condition.  A settled total that is less than the receipted
1015	        total MUST be reported as a settlement that does not match its
1016	        receipt, identified by that ref.  The identifier settlement-
1017	        mismatch SHOULD be used for this condition.  An amount on that
1018	        repeating ref that cannot be parsed as an integer MUST be
1019	        reported without abandoning the audit; the identifier malformed-
1020	        amount SHOULD be used for this condition.  A verifier MUST still
1021	        report findings for the remaining records.

1023	   10.  Aborted receipts are not matched to extract rows and are not
1024	        added to totals.

1026	   11.  Decode each checkpoint.  Reject a failed signature, and reject a
1027	        kid that does not match the key obtained for the checkpoint
1028	        issuer, on the same terms as a receipt (MUST-T4-8).  Require
1029	        receiptCount, chainHeadHash, and totals to match the receipts in
1030	        [startMs, endMs) as defined above (MUST-T11-2).  The identifier
1031	        checkpoint-total-mismatch SHOULD be used for a failed signature,
1032	        a wrong receiptCount, or totals that disagree, and checkpoint-
1033	        head-mismatch for a chainHeadHash that is not the last in-window
1034	        receipt.  If the signed totals is null, the verifier cannot
1035	        perform the totals comparison for that checkpoint.  It MUST
1036	        report that the comparison was skipped and MUST treat the
1037	        completeness guarantee as conditional; the absence of a
1038	        comparison is not a passed comparison (MUST-T11-12).  The
1039	        identifier checkpoint-totals-redacted SHOULD be used for this
1040	        condition. receiptCount and chainHeadHash MUST still be checked.
1041	        A checkpoint that fails verification MUST NOT be treated as
1042	        redacted, whatever it claims about its own totals.

1044	   12.  Every chained receipt MUST fall in exactly one checkpoint
1045	        window.  A gap or double count MUST be reported as a window
1046	        coverage failure (MUST-T11-7, MUST-T11-8).  The identifier
1047	        window-coverage SHOULD be used for this condition.

1049	   13.  Walk checkpoints in epoch order. prevCheckpointHash MUST equal
1050	        the SHA-256 of the previous checkpoint COSE bytes, or null for
1051	        genesis (MUST-T11-4).  The identifier checkpoint-total-mismatch
1052	        SHOULD be used for a broken chain, which is the fourth condition
1053	        its table row names.

1055	   14.  If two successfully verified checkpoints share an epoch number
1056	        and have different hashes, the verifier MUST report equivocation
1057	        (MUST-T11-3).  The identifier equivocation SHOULD be used for
1058	        this condition.  The checkpoints compared here are those
1059	        presented *together with* any carried by verified transparency
1060	        receipts (step 15).  Comparing only the presented chain cannot
1061	        raise this finding: MUST-T11-8, applied in step 12, requires
1062	        that chain's epochs to be consecutive, so no two of its members
1063	        share an epoch.  A copy recorded by a witness is where the
1064	        second one is found.

1066	   15.  If transparency receipts were supplied, verify them against the
1067	        out-of-band transparency key (Section 9.3); receipts that cannot
1068	        be checked that way are not evidence in either direction and the
1069	        verifier reports that it left them out (MUST-T11-15).  Discard
1070	        any whose signature fails (MUST-T11-10).  A surviving receipt
1071	        whose statement body verifies against the issuer root is a
1072	        statement that issuer published; one that does not is another
1073	        party's, and is not this issuer equivocating (MUST-T11-16).  The
1074	        survivors are the recorded statement hashes used in step 16.
1075	        Where a receipt also carries the statement body, discard that
1076	        body unless its statement hash equals the one the receipt binds
1077	        and it verifies as a checkpoint; the surviving bodies are what
1078	        step 14 compares.  Discarding a body does not discard its
1079	        receipt.

1081	   16.  Compare the surviving witness records against the presented
1082	        chain (MUST-T11-11).  For each presented checkpoint with no
1083	        surviving record, report that it is not anchored; the identifier
1084	        checkpoint-not-anchored SHOULD be used.  This is a warning: a
1085	        witness may have been configured after the checkpoint was
1086	        issued, and an operator's own gap is not evidence of
1087	        concealment.  For each surviving record whose statement is
1088	        absent from the presented chain, report that a recorded
1089	        checkpoint was withheld; the identifier checkpoint-withheld
1090	        SHOULD be used.  This is a finding and the audit MUST fail.  A
1091	        record that carries no statement body cannot say whose statement
1092	        it binds, so it MUST NOT produce this finding; it is reported as
1093	        an entry that could not be attributed and makes the guarantee
1094	        conditional, because a real withholding must not be buried by
1095	        removing the body (MUST-T11-17).  Such a record still
1096	        establishes anchoring in the first half of this step: proving
1097	        that a checkpoint was logged needs only its hash.  The verifier
1098	        MUST NOT report a withheld checkpoint as a window coverage
1099	        failure (MUST-T11-11).

1101	   17.  If any finding remains that is not a warning (a warning is a
1102	        condition that only makes the completeness guarantee
1103	        conditional), the audit MUST fail (MUST-T10-4).

1316	   A finding that puts the extract itself in doubt (extract-key-
1317	   mismatch, trust-key-unreadable, extract-scope-mismatch, or extract-
1318	   settlement-mismatch) MUST also prevent an unconditional guarantee,
1319	   not merely fail the audit.  A finding that puts a presented Trade
1320	   Manifest in doubt (manifest-key-mismatch, or trust-key-unreadable on
1321	   the manifest pin) does the same.

1323	   An unconditional guarantee therefore requires all of: an extract, a
1324	   pinned rail key the extract's signature verifies against, a stated
1325	   period the extract covers, an issuer root for whatever receipts and
1326	   checkpoints are presented, a manifest root for whatever Trade
1327	   Manifest is presented, no finding that puts the extract in doubt, and
1328	   no warning that withholds part of the comparison.  A checkpoint whose
1329	   totals were signed as withheld (checkpoint-totals-redacted) removes a
1330	   comparison the guarantee rests on, and a presented checkpoint a
1331	   supplied witness does not hold (checkpoint-not-anchored) leaves part
1332	   of the chain unwitnessed.  Either one makes the result conditional.
1333	   Anything less than the whole list is conditional, and the report MUST
1334	   say so.

1336	   An implementation MUST make the guarantee and any warnings visible in
1337	   whatever human-readable audit report it produces under this document,
1338	   not only in a returned structure (MUST-T10-14).  A report that says
1339	   the books balance while withholding that the balance is conditional
1340	   invites the reader to take a conditional result for an unconditional
1341	   one.

1343	   Checkpoints SHOULD be registered with a Transparency Service (SHOULD-
1344	   T11-5).  A test deployment MAY use an in-process append-only log as
1345	   the witness (MAY-T11-6).  Cedulon still MUST NOT take custody.

1347	   The guarantee named above is about completeness against the extract,
1348	   which is the subject of T10.  It is not a claim that no checkpoint
1349	   was suppressed.  Suppression is the subject of T11, and a report MUST
1350	   NOT be read as settling it when no witness was consulted: with no
1351	   transparency receipts, the presented chain is self-consistent by
1352	   construction and says nothing about what it left out (MUST-T11-9).  A
1353	   verifier that consulted a witness and found every presented
1354	   checkpoint recorded, with nothing recorded that was not presented,
1355	   has discharged T11 for the period those receipts cover, and for no
1356	   longer.

1358	11.  Lifecycle

1360	   1.  *Manifest.* Parties sign a Trade Manifest (optional for metered
1361	       API spend; required for goods with acceptance criteria).

1363	   2.  *Policy check.* The adapter submits a structured request to the
1364	       PDP.  Default is deny.  An allow is a Decision Token (MUST-T6-4).

1366	   3.  *Payment.* On allow, the adapter performs the x402 (or other
1367	       rail) exchange using exactly the decision fields (MUST-T6-1).
1368	       The Decision Token is consumed (MUST-T6-2).  A reused nonce is
1369	       denied (MUST-T3-1, MUST-T3-2).  A tampered or expired token is
1370	       denied (MUST-T6-5).

1372	   4.  *Receipt.* The Receipt Issuer signs a Spend Receipt.  Rail
1373	       credentials MUST NOT appear in the receipt, logs, or tool results
1374	       (MUST-T5-2, MUST-T7-1).

1376	   5.  *Dispute Evidence Bundle.* If delivery bytes do not match the
1377	       acceptance-criteria hash, an implementation MUST be able to emit
1378	       a bundle of manifest + receipt + delivery hash (MUST-T8-3).  The
1379	       bundle MUST NOT be described as an arbitral award or escrow
1380	       release (MUST-T8-4).

1382	12.  Policy Semantics

1384	   Policy is default deny.  The engine understands three families of
1385	   rule:

1387	   *  *Limit:* maximum amount per payment; maximum cumulative amount per
1388	      window (MUST-T2-2).

1390	   *  *Velocity:* maximum number of allowed payments per window (MUST-
1391	      T2-1).

1393	   *  *Scope:* optional allow-lists for payee, currency, and tool name.

1395	   Fail-closed: missing engine, crash, or exception yields deny (MUST-
1396	   T2-3).  Implementations SHOULD emit stable reason codes (SHOULD-
1397	   T2-5).  Decision tokens SHOULD expire after a short TTL (SHOULD-
1398	   T6-3).

1400	   The agent-facing spend interface MUST invoke the PDP and MUST NOT
1401	   expose a parallel ungated rail call to the model (MUST-T5-1).

1403	13.  SCITT Anchoring

1405	   A Receipt Issuer or relying party MAY construct a SCITT Signed
1406	   Statement whose payload is either the Spend Receipt COSE object or a
1407	   privacy profile (Section 14) and register it with a Transparency
1408	   Service [RFC9943].  The service returns a COSE receipt [RFC9942].
1409	   Embedding that receipt yields a Transparent Statement.  Cedulon does
1410	   not define a new transparency algorithm.

1412	   An epoch checkpoint MUST be registrable on the same terms (MUST-
1413	   T11-14).  Its Signed Statement carries the checkpoint COSE_Sign1
1414	   object as the payload and application/cedulon-checkpoint+cbor as the
1415	   content type, which is among the media types Section 16 asks to have
1416	   registered and which, until then, is a placeholder like the rest.
1417	   Nothing else about registration differs from a receipt.

1419	   This is a short section for a requirement -01 was missing, and the
1420	   omission mattered more than its length suggests. -01 asked for
1421	   checkpoints to be registered (SHOULD-T11-5) while profiling only the
1422	   receipt here, so the object carrying the suppression guarantee had no
1423	   stated form to be registered in.  Two implementations could follow
1424	   -01 to the letter and register incomparable things.

1426	14.  Privacy Considerations

1428	   A public transparency encoding MUST support omitting or hashing payer
1429	   and payee identifiers and MUST support amount redaction or bucket
1430	   encoding (MUST-T9-1).  Implementations MUST NOT write government-ID
1431	   numbers, payment-instrument PAN, or street address into a public
1432	   statement (MUST-T9-2).  Default public anchors SHOULD publish
1433	   policyHash, manifestHash, receiptHash, and timestampMs rather than
1434	   full claims (SHOULD-T9-3).  A private auditor MAY receive an
1435	   unredacted receipt out of band (MAY-T9-4).

1437	   The paragraph above counts receipt fields.  A checkpoint publishes
1438	   something a receipt does not: a per-currency total for a whole
1439	   window, which discloses trading volume even when every individual
1440	   receipt is redacted (MUST-T9-5). -01 gave no rule for it, so an
1441	   implementation could publish that total, or withhold it in a way no
1442	   verifier could recognise, and neither reading contradicted the text.

1444	   The rule is the one stated in Section 10: totals MAY be withheld by
1445	   signing it as null (MUST-T11-12), and only that form counts as a
1446	   redaction (MUST-T11-13).  The structural claims are not redactable,
1447	   because a verifier that cannot read the window or the chain head
1448	   cannot check anything at all, and a checkpoint that hid them would be
1449	   indistinguishable from a broken one.

1451	   Withholding is honest and it is also a cost: a verifier that cannot
1452	   recompute the totals says so, and the completeness guarantee for that
1453	   window is conditional.  A deployment that wants an unconditional
1454	   result publishes the totals; a deployment that wants the volume
1455	   private accepts a conditional one.  What a deployment MUST NOT do is
1456	   obtain the unconditional result while withholding the evidence for
1457	   it.

2063	15.14.  T12: Settlement without a recorded receipt

2065	   The threats above are about a counterparty, a rail or an attacker.
2066	   This one is about the issuer's own implementation, and it produces
2067	   exactly the condition the rest of this document exists to make
2068	   detectable.

2070	   An issuer that settles a payment, appends the receipt in memory and
2071	   then persists its state has three steps where it could have two
2072	   outcomes.  If the write fails, the rail holds a settlement and the
2073	   receipt exists nowhere durable.  The next start reads a state that
2074	   does not contain it, and the audit in Section 10 reports settlement-
2075	   without-receipt against an honest issuer that did everything its own
2076	   policy asked.  The evidence is missing because the issuer lost it,
2077	   not because anyone hid it, and nothing in the report can tell those
2078	   apart.

2080	     +============+==================================================+
2081	     | ID         | Requirement                                      |
2082	     +============+==================================================+
2083	     | MUST-T12-1 | An issuer MUST NOT complete a settlement whose   |
2084	     |            | receipt it cannot record durably.  The ability   |
2085	     |            | to record MUST be established before value       |
2086	     |            | moves, not after.                                |
2087	     +------------+--------------------------------------------------+
2088	     | MUST-T12-2 | Where a settlement has been made and its record  |
2089	     |            | cannot be completed, the issuer MUST undo the    |
2090	     |            | settlement in every place it still controls: in  |
2091	     |            | memory, on the rail ledger it controls, and in   |
2092	     |            | any later write it has not yet issued.  A        |
2093	     |            | refused payment MUST NOT consume the nonce or    |
2094	     |            | the payment allowance it never used.             |
2095	     +------------+--------------------------------------------------+
2096	     | MUST-T12-3 | Two issuers MUST NOT share one durable state.    |
2097	     |            | An implementation that permits it MUST fail      |
2098	     |            | loudly rather than let one writer overwrite the  |
2099	     |            | other's receipt, and the failure MUST name what  |
2100	     |            | an operator can act on.                          |
2101	     +------------+--------------------------------------------------+
2102	     | MUST-T12-4 | Where a settlement has entered a rail the issuer |
2103	     |            | does not control, and the local record cannot be |
2104	     |            | completed, the outcome is indeterminate.  The    |
2105	     |            | issuer MUST NOT treat the payment as reversed,   |
2106	     |            | and MUST NOT return the authority to spend,      |
2107	     |            | unless it holds authenticated evidence that the  |
2108	     |            | rail did not complete the settlement or that a   |
2109	     |            | reversing entry completed.                       |
2110	     +------------+--------------------------------------------------+

2112	                                  Table 20

2114	   Ordering:  Settle-then-record is the natural order to write and the
2115	      wrong one to ship.  The record is what makes the settlement
2116	      accountable, so the record is what has to be secured first (MUST-
2117	      T12-1), and a settlement that cannot be recorded has to be undone
2118	      everywhere the issuer still controls, including the nonce and the
2119	      allowance it never used (MUST-T12-2).  That undo is what the in-
2120	      process RailLedger and the session tests measure.  Once value has
2121	      entered a rail the issuer does not control, a local snapshot
2122	      cannot retract it.  Persistence failing after that point leaves
2123	      the outcome indeterminate; authority is not returned without
2124	      authenticated evidence that the rail did not complete the
2125	      settlement or that a reversing entry did (MUST-T12-4).

2127	   Recovery:  A durable-state conflict is not necessarily fatal, but it
2128	      MUST NOT be silent, and an implementation that refuses every
2129	      subsequent write without offering a way back has turned a
2130	      recoverable condition into an outage.  The reason reported has to
2131	      separate the cases an operator would act on differently (MUST-
2132	      T12-3): a write that conflicted with another writer, a write that
2133	      failed, and a state another process is holding.  A single opaque
2134	      failure leaves the operator to guess which of those happened.

2136	   Observability:  A violation of this threat is not visible in the
2137	      evidence a verifier receives.  The audit sees a settlement with no
2138	      receipt and reports settlement-without-receipt, which is the same
2139	      finding an adversary would produce, and nothing in the extract or
2140	      the receipt set distinguishes an issuer that lost the evidence
2141	      from one that hid it.  That is why the requirements here fall on
2142	      the issuer rather than on the verifier, and why an operator-facing
2143	      reason is required rather than optional.

2283	17.1.  Changes from -02

2285	   This revision has two subjects.  The first is that -02 stated a rule
2286	   for signed objects and left the implementation and the verification
2287	   algorithm without a counterpart for every object the rule applied to.
2288	   The second is T12, which no reader reported and which is not about an
2289	   adversary at all.

2291	   -02 Section 6.2 already required a verifier to obtain the public key
2292	   from an authenticated channel (a preconfigured issuer set, a
2293	   directory, or a transparency statement) and to reject a message whose
2294	   kid does not match that key (MUST-T4-8).  That rule was general.
2295	   What -02 did not carry was the verification algorithm that applies it
2296	   to each signed object, the separate root inputs a verifier supplies
2297	   out of band, and the error semantics that name a missing, unreadable,
2298	   or mismatched pin.  A companion implementation that followed the
2299	   algorithm it had, rather than that prose, still checked a Spend
2300	   Receipt, an epoch checkpoint, a Decision Token and a transparency
2301	   inclusion receipt against the key travelling inside them.  A receipt
2302	   like that silences the settlement-without-receipt finding for the
2303	   settlement it names.  The completeness property is then computed over
2304	   evidence that answers to nobody.  Section 9 states the missing
2305	   algorithm and the error semantics, and the verification algorithm now
2306	   applies them.

2308	   A reader raised the inclusion-receipt half of this against the posted
2309	   -02 after checking the archived text against the implementation
2310	   commit.  Following it into the code turned up the other three, along
2311	   with two conditions that were not about keys at all.

2313	   The first is that reporting a mismatch is not enough.  An
2314	   implementation that names a foreign key and then still lets the
2315	   receipt match its settlement has described the attack in its output
2316	   while concluding that the books balance.  MUST-T4-10 now requires the
2317	   settlement to stay reported.

2319	   The second is that an expectation which only fires when the evidence
2320	   is present can be cancelled by deleting the evidence.  A pinned payee
2321	   key with no countersignature to check was silence, so removing a
2322	   countersignature removed the question with it.  MUST-T4-14 closes
2323	   that, and MUST-T11-17 closes the same shape in the witness: an
2324	   inclusion receipt with its body stripped off can no longer bury a
2325	   withholding, while still not being allowed to accuse anyone.

2327	   T12 is new and is not about an adversary.  An issuer that settles,
2328	   appends the receipt in memory and then writes its state will, when
2329	   that write fails, leave the rail holding a settlement whose receipt
2330	   exists nowhere durable.  Restarted, it reports settlement-without-
2331	   receipt against itself.  The condition this document exists to make
2332	   detectable was reachable through the implementation's own ordering,
2333	   and no requirement in -02 said otherwise.

2335	   The same first subject carries five requirements this section has not
2336	   named so far, all of them stated in Section 9.  A pinned key that
2337	   cannot be decoded MUST NOT fall back to the keys the objects carry
2338	   (MUST-T4-11).  An issuer root may comprise more than one key, and a
2339	   verifier must accept one that does, so a rotation inside the audited
2340	   window does not force it to choose between findings against honest
2341	   receipts and abandoning the pin (MUST-T4-12).  The same out-of-band
2342	   rule reaches the payee countersignature (MUST-T4-13), the
2343	   transparency witness (MUST-T11-15 and MUST-T11-16), the Decision
2344	   Token, whose consumer issued it and therefore already holds the key
2345	   to check it with (MUST-T6-6), and a presented Trade Manifest (MUST-
2346	   T4-15).

2348	   Two requirements belong to neither subject.  MUST-T7-5 and MUST-T7-6
2349	   come from measuring the protection a stored signing key actually has
2350	   instead of deriving it from the platform.  A mount that ignores
2351	   filesystem permissions accepts the call and protects nothing, and a
2352	   writable directory or a symbolic link anywhere on the path makes the
2353	   file permission moot.  They are stated because the implementation
2354	   reported protection it did not have.

2356	   Two things are stated here that -02 got right and this revision keeps
2357	   unchanged: the extract rule itself, and the treatment of a pinned key
2358	   the verifier cannot decode.  What changed is their reach, and the
2359	   change is not backward compatible.  Where a verifier pinned the rail
2360	   key, supplied no issuer key, and was presented with receipts or
2361	   checkpoints, -02 reported the guarantee as unconditional and this
2362	   revision reports it as conditional.  Nothing about the evidence
2363	   changed; what changed is that the guarantee now says which questions
2364	   were never asked.  An audit presented with neither is unaffected, for
2365	   the reason given in Section 9.1.

2367	17.2.  Changes from -01

2369	   This revision has one subject: the checkpoint, which carries the T11
2370	   guarantee against suppression and rollback, was not wired into
2371	   anything that could discharge it.

2373	   A reader of -01 set out the gap and a second reader confirmed it
2374	   independently.  Four things were wrong at once, and they were the
2375	   same thing seen from four sides.  The SCITT anchoring section
2376	   profiled the Spend Receipt and not the checkpoint, so SHOULD-T11-5
2377	   asked for checkpoints to be registered without saying in what form
2378	   (MUST-T11-14 now says).  None of the steps of the verification
2379	   algorithm read a transparency receipt, so a deployment could follow
2380	   SHOULD-T11-5 to the letter and still have a verifier that never
2381	   consulted the witness (steps 15 and 16 now do).  MUST-T11-3,
2382	   equivocation, could not fire at all: the only checkpoints compared
2383	   were the presented ones, and MUST-T11-8 requires those to be
2384	   consecutive, so no two of them can share an epoch.  A second copy is
2385	   found in a witness, and nothing brought one in.  And the checkpoint
2386	   binds a per-currency total for a window while the privacy section
2387	   counted only receipt fields, so a window total could be published, or
2388	   withheld, with no stated rule either way.

2390	   The repairs are MUST-T11-10 through MUST-T11-14.  The transparency
2391	   receipt is a new optional input; supplying none leaves the verifier
2392	   behaving exactly as in -01, which is deliberate, because the point of
2393	   the witness is to add a claim that could not be made before, not to
2394	   withdraw one that could.

2396	   Two decisions inside those repairs are worth stating on their own,
2397	   because a reader might reasonably have expected the other choice.

2399	   *  A recorded checkpoint the presented chain omits gets its own
2400	      identifier, checkpoint-withheld, rather than being folded into
2401	      window-coverage (MUST-T11-11).  The reporter asked which way it
2402	      should go.  Coverage says the record shown is incomplete; a
2403	      withheld checkpoint says the party under audit is holding a record
2404	      it did not show.  An operator who sees one identifier for both
2405	      cannot tell an incomplete record from a concealed one, which is
2406	      the distinction the whole threat is about.

2408	   *  A checkpoint with no receipt in a supplied witness is a warning
2409	      rather than a failure.  A witness may be configured after
2410	      checkpoints have already been issued, and an operator's own gap in
2411	      anchoring is not evidence that anything was concealed.  The
2412	      asymmetry is deliberate: what the witness holds and the chain does
2413	      not is a finding, what the chain holds and the witness does not is
2414	      a warning.

2416	   One change is not a repair of -01 but of the first attempt at this
2417	   revision, and it is recorded because the failure is instructive.
2418	   Signed totals were first made redactable through a field carried
2419	   alongside the checkpoint rather than inside the COSE payload.
2420	   Anything outside the signature is chosen by whoever presents the
2421	   object, which here is the party under audit, so a checkpoint whose
2422	   signed totals disagreed with its receipts could be re-presented as
2423	   redacted and the mismatch went unreported.  Redaction is now inside
2424	   the signature and a redaction asserted anywhere else MUST be ignored
2425	   (MUST-T11-12, MUST-T11-13).  This was the same shape as the bypass
2426	   -01 was written to close: a check that a party under audit could
2427	   switch off.

2429	   Reversal, refund, partial settlement, and the escrow role remain out
2430	   of scope and are still expected later, with no date. -01 said the
2431	   same and this revision does not improve on it.

2433	   The reporters are named in the Acknowledgments.

2435	18.  Evolution and Future Work (Informative)

2437	   This section is a direction, not a commitment.  The structures below
2438	   are reserved in name only.  Normative wire formats, tests, and
2439	   threat-model MUST lines for them belong in later revisions (-03 or
2440	   later), written with the same discipline as this -02.

2442	18.1.  Re-attestation profile

2444	   Algorithms retire.  A Spend Receipt or checkpoint signed under
2445	   Ed25519 today may need a later verifier that no longer accepts -19.
2446	   A companion seed [REATTEST] sketches re-attestation: register the
2447	   original COSE bytes as a SCITT Signed Statement and have a current
2448	   algorithm countersign or receipt them.  The principle is that
2449	   structures outlive ciphers.  The first concrete example is the
2450	   profile's own move from generic EdDSA (-8) to Ed25519 (-19) in
2451	   [RFC9864].

2453	18.2.  Streaming reconciliation

2455	   Epoch checkpoints in this document are batch windows.  A later
2456	   revision may define a continuous, second-scale profile [STREAMING] in
2457	   which the same completeness relation is evaluated as settlements
2458	   arrive, without waiting for an epoch close.  That work does not
2459	   change the matching rules in this document, and it did not arrive in
2460	   this revision either.

2462	18.3.  Generalization

2464	   Payment is the special case that this -02 implements.  The same
2465	   completeness calculus (an authenticated extract of consumed units
2466	   reconciled to signed receipts) can apply to other consumable
2467	   resources such as compute, data, or energy.  This document does not
2468	   specify those profiles.

2470	19.  Informative Notes on Adjacent Protocols

2472	   x402 [X402] uses HTTP 402 [RFC9110] to negotiate stablecoin payment.
2473	   AP2 [AP2] uses signed mandates as verifiable credentials.  Cedulon
2474	   does not replace either protocol.  Profiles built on HTTP Message
2475	   Signatures [RFC9421] authenticate bots; they are not a spend receipt.
2476	   draft-bates-atp [BATES-ATP] is a lineage neighbor.  It does not
2477	   define rail-extract completeness.

2479	   draft-vauban-x402-stark-receipts [VAUBAN] specifies complementary
2480	   x402 receipt-format variants that a Cedulon Spend Receipt MAY carry
2481	   as a rail proof; it does not define rail-extract completeness. draft-
2482	   schrock-ep-outcome-binding [SCHROCK] compares authorized action bytes
2483	   to independently observed effects; it does not define rail-extract
2484	   completeness. draft-marques-asqav-compliance-receipts [MARQUES]
2485	   profiles access-control action receipts (the broader Acta family
2486	   includes [ACTA]); it does not define rail-extract completeness.
2487	   draft-hopley-x402-compliance-receipt [HOPLEY] records an admission-
2488	   time compliance decision; it does not define rail-extract
2489	   completeness.
